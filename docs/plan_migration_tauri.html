01

Objectif et principe

Remplacer l'interface CustomTkinter (app_ctk.py) par une interface Tauri v2 + React, celle de la maquette validée, sans réécrire ce qui marche déjà. Le moteur Python (agent/) reste tel quel : il devient un programme sans fenêtre que l'interface pilote par messages JSON.

On change la vitrine, pas la mécanique

agent/ (ffmpeg, HEIC, métadonnées, calendrier, licence) marche et a été testé en vrai. Le réécrire en Rust ou en TypeScript prendrait des mois et ajouterait des bugs.

L'ancienne app reste en service

app_ctk.py continue de marcher et d'être livrée jusqu'à ce que la nouvelle fasse tout ce qu'elle fait. Rien n'est supprimé avant la phase 6.

Un morceau à la fois

Chaque phase livre quelque chose d'utilisable et de vérifiable. Si on s'arrête en route, rien n'est cassé : l'ancienne app tourne toujours.

Ce qui change
  • L'interface : React + Tailwind v4, police Geist, bleu de marque #4c6fff (celui du site).
  • La progression s'affiche dans la page, plus de fenêtre « Veuillez patienter ».
  • Des notifications intégrées à la place des boîtes messagebox.
  • Les appels réseau (licence) ne gèlent plus jamais la fenêtre.
Ce qui ne change pas
  • agent/ et ses fonctions : même code, mêmes résultats.
  • Les données dans %APPDATA%\HelpVA : licence, paramètres, calendrier.
  • L'empreinte du PC, calculée par le même Python : aucune réactivation.
  • Le serveur Supabase, la clé publique Ed25519, les textes affichés.
i
Pourquoi Tauri ? Il affiche l'interface avec WebView2, le moteur d'Edge déjà présent sur Windows 10/11 : tout le web moderne, sans embarquer un navigateur entier comme Electron. L'exécutable reste léger.

1.1 Comment ça marche, en 4 temps

  1. 1
    Démarrage. Le cœur Rust lance le moteur (helpva-engine.exe) sans fenêtre de console et attend son message pret. Le moteur l'envoie tout de suite, avant de charger les bibliothèques lourdes (Pillow, numpy) : l'écran s'affiche vite.
  2. 2
    Commande. L'interface envoie par exemple mp4_convertir. Rust l'écrit sur l'entrée standard du moteur, en une ligne JSON.
  3. 3
    Travail. Le moteur appelle la fonction de agent/ et renvoie des lignes progress et log, puis un result (ou une error). Rust les transmet à l'interface sous forme d'événements.
  4. 4
    Fermeture. Rust envoie quitter. Si l'app plante, le moteur voit son entrée se fermer et s'arrête seul ; Windows tue aussi ses ffmpeg grâce à un « Job Object ». Aucun processus ne reste en arrière-plan.
i
Pourquoi c'est Rust qui lance le moteur ?

Les permissions Tauri (capabilities) filtrent ce que la page web a le droit de faire. Si le JavaScript pouvait lancer des programmes, une seule faille dans l'interface suffirait pour exécuter n'importe quoi. Lancé depuis Rust, le moteur reste hors de portée : l'interface n'a aucune permission « shell », elle peut seulement lui parler.

!
Développer sans Rust : le pont de dev

Rust n'est pas encore installé. En attendant, l'interface tourne dans Edge (npm run dev) et parle au moteur via un petit serveur Python local. Le client TypeScript choisit seul : isTauri() vrai → vrai moteur via Rust, sinon → le pont. Les écrans ne voient aucune différence.

03

Le protocole du moteur

Une ligne = un objet JSON. L'interface envoie des requêtes {id, cmd, args}, le moteur répond par des événements qui reprennent le même id. Règle d'or : le moteur décide et valide, l'interface affiche.

# → = interface vers moteur (stdin) ← = moteur vers interface (stdout)← {"id":null,"type":"pret","nom":"HelpVA","version":"1.0.0","protocole":1,"pid":8124,"frozen":true}→ {"id":"c-12","cmd":"mp4_convertir","args":{"source":{"type":"dossier","chemin":"C:\\…\\Shooting juin"}}}← {"id":"c-12","type":"progress","fraction":0.38,"texte":"Dossier 2/3 — Modèle A\nVidéo 1/4 · clip_07.mov — 43 %","details":{…}}← {"id":"c-12","type":"log","flux":"stdout","niveau":"info","texte":"[convert] (1/4) clip_07.mov…"}→ {"id":"c-13","cmd":"annuler","args":{"cible":"c-12"}}← {"id":"c-13","type":"result","data":{"etat":"annulation_demandee"}}← {"id":"c-12","type":"result","data":{"traites":4,"echecs":[],"arrete":true,"dossiers":3,"sortie":"…\\media (mp4)"}}← {"id":"c-14","type":"error","code":"OCCUPE","message":"Une action est déjà en cours, patientez…"}

Accents montrés en clair pour la lisibilité. Sur le fil, le moteur écrit en ASCII pur (é devient \u00e9) : la page de code Windows (cp1252) ne peut alors plus rien casser, et JSON.parse décode tout normalement.

3.1 Les six règles à retenir

  1. 1
    Un seul événement final par requête : result ou error. Avant lui, autant de progress et de log que nécessaire.
  2. 2
    Annuler n'est pas une erreur. La tâche se termine par un result avec arrete: true ; les fichiers déjà faits restent.
  3. 3
    Refus métier ≠ plantage. Un code d'activation refusé donne un result avec ok: false. error veut dire « la commande n'a pas pu s'exécuter ».
  1. 4
    Une seule tâche longue à la fois, sinon OCCUPE. Les requêtes rapides (licence, paramètres, calendrier) passent même pendant une conversion, 4 en parallèle.
  2. 5
    stdout est réservé au protocole. Les print() de agent/ sont captés et deviennent des événements log : ils ne peuvent plus casser le JSON.
  3. 6
    Poignée de main. pret annonce protocole: 1. Si l'interface attend une autre version, elle affiche « Réinstallez HelpVA » au lieu de mal comprendre le moteur.

P0

Socle : moteur, pont de dev, client TypeScript, module MP4 réel

Prouver toute la chaîne sur un vrai module : interface React → moteur Python → vraie conversion MP4, sans Rust.

En cours≈ 3 à 5 jours

Livrables

  • engine/ : protocole JSON-lines, tâche longue unique + annulation, journal, pret / quitter / fin d'entrée, Job Object.
  • agent/ : ffmpeg sans entrée standard, détails de progression (retouches compatibles).
  • Pont de dev (127.0.0.1 + jeton) et client src/moteur/ à deux transports.
  • desktop/ créé depuis la maquette ; Convertir en MP4 branché sur le vrai moteur ; tests unittest.

Critères de fin

  • python -m unittest passe, sans toucher au vrai %APPDATA%\HelpVA.
  • Dans Edge : 3 sous-dossiers convertis, progression et journal identiques à l'ancienne app.
  • Annuler : arrêt en moins d'une seconde, fichier partiel supprimé ; double clic → OCCUPE.
  • Pont fermé : plus aucun python ni ffmpeg ; app_ctk.py convertit toujours.
P1

Licence et premier lancement

Reproduire la machine à états de la licence à l'identique, sans jamais geler la fenêtre.

À faire≈ 3 à 4 jours

Livrables

  • Écran « Vérification de la licence… » : hors ligne, l'appel peut durer environ 40 s.
  • 8 raisons → Bienvenue, « Connexion internet requise » (essai auto à 20 s) ou Activation (4 variantes, textes exacts).
  • Bandeau hors-ligne + rappel de fin, empilés ; re-contrôle toutes les heures (5 min hors-ligne), qui rafraîchit aussi la barre latérale.
  • Moteur : commandes licence_* et garde LICENCE_REQUISE.

Critères de fin

  • Chaque raison mène au bon écran (licence simulée en test, puis un vrai code de test du tableau de bord).
  • Licence de l'ancienne app reconnue sans réactivation (même empreinte).
  • Fenêtre fluide pendant les appels réseau ; le minuteur de 20 s ne s'empile plus.
  • Un blocage pendant une tâche l'annule proprement d'abord.
P2

Accueil, Paramètres, thème et cadre de l'app

Tout ce qui entoure les modules : barre latérale, Accueil, Paramètres, fenêtre.

À faire≈ 2 à 3 jours

Livrables

  • Barre latérale : marque, navigation, carte utilisateur, version, bouton du thème.
  • Accueil : « Hello, {nom} », Dossier de sortie, Conseil, les 4 modules.
  • Paramètres : dossier de sortie (Changer / Ouvrir / Réinitialiser), licence, Résilier.
  • Fenêtre 1160×760 (min. 980×640) ajustée à l'écran ; journal gardé entre les pages.

Critères de fin

  • parametres.json partagé : un réglage fait dans une app est relu par l'autre.
  • Rendu vérifié en clair et en sombre, à 980×640, zoom Windows 125 et 150 %.
  • Dates et libellés d'abonnement identiques à l'ancienne app.
P3

Convertir les images + Changer les métadonnées

Les 3 modules restants sont Images, Métadonnées et Ranger. Ranger, le plus gros, a sa propre phase.

À faire≈ 3 à 4 jours

Livrables

  • Composant commun : source, « Remplacer ? », progression, résultat avec échecs, « Ouvrir le dossier ».
  • Images : JPG ou PNG, HEIC/HEIF ; sortie images (jpg) / images (png).
  • Métadonnées : « Renommer (1, 2, 3…) » coché, arborescence gardée ; sortie … (métadonnées changées).

Critères de fin

  • Même entrée → même nombre de fichiers et même arborescence que l'ancienne app.
  • Après annulation, le processeur redescend ; une sélection de 3 000 fichiers passe.
  • Fichiers illisibles listés (les 5 premiers + « … »).
P4

Ranger les médias + éditeur de calendrier

Le module le plus riche : 3 étapes, des validations, et l'éditeur de semaines refait dans la page.

À faire≈ 4 à 6 jours

Livrables

  • Page en 3 étapes : calendrier et types mémorisés, un dossier par type analysé, répartition au hasard.
  • Validations + récapitulatif avant lancement ; résultat avec manques et surplus.
  • Éditeur dans la page : 2 modes, semaines, créneaux, besoins en direct, Enregistrer.

Critères de fin

  • calendrier_utilisateur.json échangé sans perte entre les deux apps.
  • Mêmes sources, hasard coupé → même arborescence qu'avec l'ancienne app.
  • Carrousels dans l'ordre 1, 2, 3 ; éditeur fluide avec 20 semaines.
P5

Empaquetage Windows : moteur, installeur, WebView2, signature, migration

Livrer HelpVA 2.0 comme une mise à jour normale de la 1.0 : le client installe et retrouve tout.

À faire≈ 4 à 6 jours

Livrables

  • Moteur PyInstaller en mode dossier (sans tkinter), dans les ressources Tauri (moteur/), lancé par Rust.
  • Rust : moteur.rs, mutex HelpVA_Instance, CSP stricte, identifiant définitif, HelpVA.exe.
  • Installeur avec le même AppId, WebView2 installé s'il manque, moteur arrêté avant la copie.
  • Signature de code (selon budget) ; un seul script de build.

Critères de fin

  • Windows propre (Bac à sable Windows) : démarre, convertit, se ferme sans processus restant.
  • Mise à jour 1.0 → 2.0 : une seule ligne HelpVA, licence et réglages conservés.
  • Désinstallation : %APPDATA%\HelpVA conservé.
Pourquoi le mode dossier ? En « un seul fichier », PyInstaller décompresse environ 200 Mo dans %TEMP% à chaque lancement, et les y laisse si le moteur est tué. Plus lent, et plus souvent signalé par les antivirus.
Installeur 2.0PourContre
Inno Setup RECOMMANDÉ Même AppId que la 1.0 : la 2.0 la remplace automatiquement. AppMutex, langues FR/EN et images déjà prêts. Incompatible avec la mise à jour automatique intégrée de Tauri (plugin updater).
NSIS (Tauri) Mise à jour automatique possible ; gestion de WebView2 intégrée. Autre clé de registre : il faut désinstaller la 1.0 par un script, avec un risque de double entrée.
P6

Recette complète, parité, bascule

Vérifier que la nouvelle app fait tout ce que faisait l'ancienne, puis supprimer l'ancienne.

À faire≈ 3 à 5 jours + pilote

Livrables

  • Checklist de parité (section 7) cochée à 100 %, ou écarts acceptés par écrit.
  • Pilote de 1 à 2 semaines chez 2 ou 3 agences ; HelpVA 2.0.0 publiée.
  • Tag v1-ctk, puis suppression de app_ctk.py, customtkinter et de l'ancien HelpVA.spec ; docs à jour.

Critères de fin

  • Aucun bug bloquant pendant le pilote ; tests verts ; build reproductible.
  • La suppression est un commit séparé, fait par Christ, réversible grâce au tag.
P7

macOS et Linux

Même app, mêmes écrans. Seuls le build et la signature changent.

Plus tard≈ 5 à 8 jours

Livrables

  • macOS : build sur un Mac (pas de compilation croisée), moteur dans Contents/Resources, signature + notarisation Apple (99 $/an).
  • Linux : .deb / AppImage (webkit2gtk 4.1) ; les specs mac et linux deviennent des specs du moteur.

  • Clients Mac existants : même empreinte, pas de réactivation.

Total pour Windows (P0 à P6) : environ 6 à 8 semaines de travail, pilote compris. Ordre de grandeur seulement.

Les étapes, dans l'ordre

  1. 1
    Ouvrir Visual Studio Installer → Build Tools 2022 → Modifier → cocher « Développement Desktop en C++ » (laisser cochés MSVC v143 et le SDK Windows 11) → Modifier. Redémarrer si c'est demandé.
  2. 2
    Créer D:\rust, puis 3 variables d'environnement utilisateur (menu Démarrer → « Modifier les variables d'environnement pour votre compte ») : RUSTUP_HOME=D:\rust\rustup, CARGO_HOME=D:\rust\cargo, CARGO_TARGET_DIR=D:\rust\target. Pourquoi : rustup et cargo installent là où ces variables pointent, au lieu de C:\Users\…\.rustup.
  3. 3
    Télécharger rustup-init.exe sur rustup.rs (winget n'existe pas sur ce PC) et le lancer → choix 1 (installation standard).
  4. 4
    Fermer et rouvrir le terminal, puis vérifier : rustc --version et cargo --version.
  5. 5
    Dans desktop/ : npm run tauri info (tout doit être vert), puis npm run tauri dev. La première compilation prend 5 à 10 minutes ; les suivantes, quelques secondes.

  4. 4
    Checklist cochée pour les points de la phase, et app_ctk.py relancée pour vérifier qu'elle marche encore.
  5. 5
    Christ relit et commite lui-même, un commit par étape : on sait toujours où revenir si quelque chose casse.
07
